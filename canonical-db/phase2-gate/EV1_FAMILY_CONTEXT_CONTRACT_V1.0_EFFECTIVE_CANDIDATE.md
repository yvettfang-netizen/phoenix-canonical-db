## 1. 证据边界

1. 本合同是新库的前瞻性基线，**不是**历史 Family Context V1 的修订稿；历史原件仍然缺失。（来源：BC 证据边界；FCA；FD-2）
2. 历史原件如果找回，须逐条比对；有冲突时另行修订，**不追溯改动已登记的 Migration**。（FD-2）
3. 本阶段不导入旧 ID、旧数据，不复用 Founder OS / Operations 的资产。（FD-3、FD-4；V1.4 第 1 节）

## 2. 标识

1. **内部主键：** 一律为应用签发的 UUIDv7，数据库在边界处校验；PostgreSQL 序列和 UUIDv4 不具备身份权威。（BC FC-2；FCA 1）【已实现：M0003 `core.is_uuid_v7`】
2. **公开 ID：** 格式为 `per_ / fam_ / stu_ / gdn_ + 32 位十六进制`，经 `integration.public_ids` 显式映射；格式本身不证明身份或权限。（BC FC-4；FCA 2；FD-2.3）【已实现：M0003】
3. **`usr_`：** 预留给登录主体，使用前另行实现。（FD-2.3）【未实现】
4. **旧 ID：** 只能按"来源系统 + 实体类型 + 旧 ID"映射，状态为 PENDING / VERIFIED / REVOKED / SUPERSEDED；同一来源元组只允许一条有效的 VERIFIED 映射。姓名、电话、邮箱或 ID 形状都**不能**确立等同关系。（BC FC-4、FC-5；FCA 3）【表结构已实现：M0003；本阶段不使用，V1.4 EV-5】

## 3. 自然人、学生与家庭

1. `core.people` 是唯一的自然人主数据；自然人不需要有登录账号。（BC FC-1、FC-3；FCA 4）【已实现：M0003】
2. **学生**是自然人的一对一档案（`core.student_profiles`），不是另一种人。（BC FC-3）【已实现：M0003】
3. **家庭成员关系：**
   - 有角色（PRIMARY / MEMBER）和有效期；
   - 同一家庭中每人只有一条成员关系。
   
   （M0003）【已实现】
4. **成员关系不自动授予文件访问权：** 访问文件须有有效 Consent；代他人操作时，还须有有效监护授权。（BC FC-7；FCA 4）【已实现】
5. **字段白名单：** 自然人与家庭目前只有展示名称；联系方式等扩展字段须另行批准。（FD-2.6）【已实现】
6. **谁能创建：** 家庭、自然人、成员关系、学生档案只能由 INTERNAL 渠道的 SERVICE 主体创建。（FD-2.6）【已实现：M0009】
7. **首个家庭的创建：** INTERNAL 服务上下文可以不绑定家庭，但只用于创建家庭和管理操作；凡是作用于某个家庭内部的操作，仍须绑定该家庭。（D-10 第 1 条）【待实现：0012 起】

## 4. 登录主体与可信上下文

1. **归属：** `auth` 拥有登录主体和可信会话上下文；`core` 拥有自然人、家庭和家庭关系。（BC FC-1）【已实现】
2. **主体类型：** FAMILY / ADVISOR / CHANNEL / SERVICE。
   - FAMILY、ADVISOR、CHANNEL 主体必须对应且仅对应一个自然人；
   - SERVICE 主体不对应自然人。
   
   这是对 BC 中"A principal may reference one Person"一句的解释。（D-11 第 1、4 条）【待实现：0012 起】
3. **SERVICE 主体：** 只由安装或运维流程以 migrator 或 bootstrap 创建和停用，不对 app 开放，全程审计。（D-10 第 2 条）【待实现】
4. **其他登录主体：** FAMILY / ADVISOR / CHANNEL 登录主体只能经管理接口建立和停用，管理接口只允许 INTERNAL 渠道的 SERVICE 主体调用。（D-10 第 3 条）【待实现】
5. **外部身份映射：**
   - 外部身份以"签发方 + subject"唯一对应一个主体；
   - 未登记的身份一律拒绝，不自动开户；
   - 停用的主体或映射立即失效。
   
   （V1.3 FD-6 第 3 条）【待实现：D7】
6. **用户认证：** 由应用后端以 OIDC / JWT 完成，只接受非对称签名；数据库不接收用户令牌。（BC 可信会话第 4 条；V1.3 FD-6 第 1、2 条）【应用侧，待接入】
7. **可信上下文：**
   - binder 与应用分开账号、分开连接池（BC 可信会话第 1 条；V1.3 FD-6 第 4 条）；
   - 每个请求使用一张一次性票据，有效期不超过 60 秒（FD-2.5；V1.3 FD-6 第 5 条）；
   - 上下文按后端进程标识（PID 加启动时间）存放（M0007）；
   - 每次判定都检查是否过期（BC 可信会话第 3 条）；
   - 连接归还前清除上下文，清除失败的连接丢弃；禁止事务级连接池（FD-2.5；V1.3 FD-6 第 6 条）；
   - 客户端提供的人员、家庭 ID 一律不被信任。
   
   【数据库侧已实现：M0007 / M0008；连接池行为待应用接入】
8. **INTERNAL 上下文：** 签发和绑定时，INTERNAL 渠道要求 SERVICE 主体且不设操作人自然人；其他渠道要求操作人与主体对应的自然人一致。（D-11 第 3 条）【待实现】

## 5. 民事能力

1. 每个自然人有一项"已核验的民事能力"：`ADULT_VERIFIED` / `MINOR_VERIFIED` / `UNVERIFIED`，默认 `UNVERIFIED`。（D-12 第 1 条）【已实现：M0011】
2. **记录方式：**
   - 每次设定都记录证据引用、核验人（principal）和核验时间；
   - 只追加，不可原地修改；
   - 只有 INTERNAL 渠道的 SERVICE 主体可以设定。
   
   （D-12 第 1 条）【已实现：M0011】
3. **年龄门槛：** 18 岁，由核验流程判定；数据库不推断年龄或法域。改为 14 岁须另行书面决定。（D-12 第 5 条；BC FC-6）【已实现：数据库只存核验结果】

## 6. 监护授权

1. **性质：** 监护是同一家庭内两个自然人之间、有时间限制的关系与授权，不是另一种人；血缘关系本身不授予任何文件访问权。（BC FC-3；FCA 4）【已实现：M0003】
2. **证据等级：** `VERIFIED` 或 `SELF_DECLARED_LEGACY`。`SELF_DECLARED_LEGACY` 永远不能授权身份类文件，也**不能经 API 新建**。（BC FC-6；D-10 第 3 条）【等级已实现；API 限制待实现】
3. **范围：**
   - 取值为 `GENERAL` / `EDUCATION` / `IDENTITY`，**精确匹配**；`GENERAL` 不覆盖身份类；
   - 身份类须为 `IDENTITY` 范围且证据等级为 `VERIFIED`。
   
   （FD-2.2）【已实现】
4. **不可原地改：** 证据等级不可原地修改；升级或降级须新建授权记录，旧记录终止，并留审计。（FD-2.4）【已实现：M0007】
5. **状态：** 生命周期为 ACTIVE / REVOKED / EXPIRED，同一组合只允许一条 ACTIVE。（M0007）【已实现】
6. **建立与撤销：**
   - 只经 SERVICE 管理接口进行；
   - 建立 `VERIFIED` 级授权须附证据引用并记录核验人。
   
   （D-10 第 3 条）【待实现】
7. **双人复核：** 导入真实数据前，建立 VERIFIED 监护授权须两人复核；撤销不受限制。（V1.4 第 5 节）【真实数据前实现】

## 7. Consent

1. **范围：** Consent 按授权人、被授权人、主体、家庭、用途、数据类别限定。（BC Consent 第 1 条）【已实现：M0003】
2. **用途与数据类别的合法组合：**
   - 用途 `DOCUMENT_READ` 可配三种数据类别：`GENERAL`、`EDUCATION`、`IDENTITY_SENSITIVE`；
   - `EDUCATION_CASE` 只配 `EDUCATION`；
   - `IDENTITY_CASE` 只配 `IDENTITY_SENSITIVE`。
   
   （M0011 `consent.actor_can_grant`）【已实现】
3. **状态：** ACTIVE / WITHDRAWN / EXPIRED。撤回在下一次判定时生效；原始授予时间与撤回时间不可修改；到期以判定时刻为准。（BC Consent 第 2 条）【已实现；见第 11 节 E1-5】
4. **谁能授予：**
   - 只能在 FAMILY 渠道；
   - 本人为 `ADULT_VERIFIED` 时可以自行授予；
   - 否则只能由范围匹配、VERIFIED 等级的有效监护人代授。适用于所有用途和数据类别。
   
   （D-12 第 2、3 条）【已实现：M0011】
5. **谁能撤回：** 本人（不论民事能力）或有效监护人，不设能力门槛。（D-12 第 4 条）【已实现：M0011】
6. **生效对象：** Consent 只对被授权人本人生效；判定时检查被授权人是否为当前操作人。（M0003 `consent.has_active_consent`）【已实现】

## 8. 顾问与渠道方

1. **顾问：** 须有有效的个案分配，并持有所需 Consent。（BC Consent 第 4 条）【已实现；分配范围见第 11 节 E1-4】
2. **渠道方：** 须有针对具体主体的有效渠道授权，并持有所需 Consent。（BC Consent 第 4 条）【已实现】
3. 两者都不得跨家庭。（BC）【已实现】
4. **基本展示信息：** 顾问或渠道方查看被分配或被授权学生的基本展示信息，不需要额外 Consent；查看申请、身份案件和文件仍须相应 Consent。（FD-2.1）【已实现】
5. **授权管理：** 顾问分配、渠道授权的建立与撤销只经 SERVICE 管理接口进行；建立顾问、渠道登录主体在导入真实数据前须两人复核。（D-10 第 3 条；V1.4 第 5 节）【待实现】

## 9. 审计

1. 每一个可能拒绝的业务动作，都通过受控函数向 `audit.access_events` 写入稳定的原因代码。（BC 可信会话第 5 条）【已实现】
2. 每次写入判定同时写一条服务器日志，前缀 `PHOENIX_AUDIT`，只写 ID 和代码，客户端回滚抹不掉。（D-9）【待实现】
3. 服务操作的操作人记录为 principal。（D-11 第 2 条）【待实现】
4. 网关侧记录请求级审计，请求编号贯穿网关与数据库。（V1.3 FD-6 第 7、8 条）【待实现：D7 与应用侧】

## 10. 数据库角色

1. **各角色只做自己的事：**
   - migrator：只做 DDL 与迁移账本；
   - binder：只做绑定与清除上下文；
   - app：只经受控函数写入，经 RLS 读取；
   - reader：只读经 RLS 过滤的元数据，可读迁移账本；
   - bootstrap：只用于安装。
   
   （BC 角色边界；R-8 / M0010）【已实现】
2. 日常业务不得以超级用户写入；超级用户只用于安装和 Migration。（D-10 第 5 条）【测试夹具改造待实现】
