# 08 · 回滚与恢复手册（Rollback / Recovery Runbook）

**原则（FD-7 第 8 条）：**
- 回滚窗口为变更后 24 小时；
- 优先用新的 Migration 向前修复；
- 需要回退数据时，从变更前的备份恢复到**新的**容器或卷，核对后再切换；
- **不在原数据卷上直接覆盖恢复**。

**状态：** 本手册中的每个机制都已在本地演练（证据见各节）；从未在生产环境执行。

## 1. 情形与处置

| 情形 | 现象 | 处置 | 已演练 |
|---|---|---|---|
| A. 升级时某个 Migration 失败 | `install.sh` 报错退出 | 失败的那个已整体回滚（原子包装），之前已成功的保留，账本准确。执行预检，修正原因后重跑 `install.sh`。不需要恢复备份 | 是：0012 阻断，`evidence/v1.8-upgrade-path-*.txt` |
| B. 升级成功，但发现缺陷（窗口内） | 测试或告警发现行为错误 | 编写修复 Migration（新编号），按 `07` 第 2 节发布。**不修改历史 Migration** | 是：0016 修复 V16-F1–F3 即此流程 |
| C. 需要回退数据（窗口内） | 数据被错误修改 | ① 停止 binder 与应用；② 新建 compose 项目和全新卷；③ 用变更前的已校验备份执行 `restore.sh`；④ 健康检查与核对；⑤ 切换应用连接；⑥ 原卷保留为证据，不删除 | 是：`evidence/v1.8-deploy-rehearsal.txt` 第 6–7 步 |
| D. 备份文件疑似被篡改 | `restore.sh` 报 `digest mismatch` | 不使用该备份；选更早的已校验备份；按 S1 事件处理 | 是：第 6 步篡改被拒 |
| E. 审计链断裂 | `alert_check.sh` 报 `AUDIT_CHAIN_BROKEN` | 按 S1 处理：封存现场，对比服务器日志原件与提取文件，查明原因；不得重写已提取的文件 | 是：第 13 步 |
| F. 迁移账本与文件不一致 | `alert_check.sh` 报 `LEDGER_MISMATCH` | 按 S1 处理：停止发布，核对部署包哈希（`02`）与 Git 提交 | 由告警脚本覆盖 |
| G. 凭据疑似泄露 | — | 按 S1 处理：轮换口令（先加新、验证、再撤旧，F-16）；停用相关登录主体与外部身份映射（会立即失效）；检查审计 | 停用即时生效：`f10_v18` |

## 2. 恢复命令（情形 C）

```bash
# 在新的部署目录（独立 compose 项目、全新卷）中执行：
cp <旧部署目录>/backups/phoenix_canonical_<stamp>.dump{,.manifest.json} backups/
./restore.sh backups/phoenix_canonical_<stamp>.dump   # 先校验清单摘要；目标必须是全新的库
./health.sh
./restore_drill.sh backups/phoenix_canonical_<stamp>.dump   # 可选：在一次性容器中再核对一次账本
```

## 3. 事件分级（FD-7 第 7 条）

| 级别 | 情形 | 响应 |
|---|---|---|
| S1 | 怀疑数据或凭据泄露、未授权访问、账本不一致、审计链断裂 | 立即通知 Founder；15 分钟内响应；先封控、后排查 |
| S2 | 备份或恢复演练失败、数据库不可用、对账异常 | 4 小时内响应 |
| S3 | 其他告警 | 下一个工作日 |

## 4. 不可做的事

- 不改写已登记的 Migration；
- 不在原卷上恢复；
- 不删除审计提取文件和服务器日志原件；
- 不用超级用户直接改业务数据来"修复"；
- 不把口令写进命令行、日志或聊天。
