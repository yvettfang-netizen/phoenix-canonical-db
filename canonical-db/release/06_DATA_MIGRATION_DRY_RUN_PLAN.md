## 2. 将来真实数据迁移的演练方法（未执行）

前提（全部满足才可开始）：
1. 立项批准，FD-8 第 3 项另行审批；
2. EV-5 旧数据源清单齐全：来源系统、表或文件、负责人、ID 格式、冲突与替代策略；
3. EV-2：如涉及 Founder OS，须有原件与哈希；
4. 双人复核已实现（补充 V1.4 第 5 节）；
5. 服务器闸门 G-1 至 G-8 已关闭；
6. FD-7 的 RPO / RTO 已重新决定，届时建议采用 WAL 归档加 PITR。

| 步骤 | 内容 | 产出 |
|---|---|---|
| D1 | 来源清点（只读）：每个来源的记录数、ID 形态、敏感数据类别 | 清点报告，不含个人数据 |
| D2 | 映射规则：按"来源系统 + 实体类型 + 旧 ID"写入 `integration.legacy_id_mappings`，初始状态 PENDING；**禁止**用姓名、电话、ID 形状判定为同一人（EV-1 第 2.4 条） | 映射规格 |
| D3 | 去标识化演练库：在隔离环境中，用去标识化或合成的副本跑完整导入；不使用真实个人数据 | 演练报告 |
| D4 | 经 API 导入：一切写入都经过 SERVICE 管理接口和业务 API（不用超级用户直接写），因此 D-9 审计、RLS、合同规则全部生效 | 审计对账为 0 异常 |
| D5 | 核对：行数、映射状态（只允许 VERIFIED 的生效）、监护证据等级、民事能力来源、文件元数据（真实对象存储前，EV-6 须完成） | 核对报告 |
| D6 | 回退：导入失败时整批回滚；按 `08` 用导入前备份恢复 | 回退演练记录 |
| D7 | 双人复核：VERIFIED 监护授权、民事能力、顾问 / 渠道登录主体都须两人确认 | 复核记录 |

## 3. 已知的数据前提（来自 Migration 约束）

| 约束 | 影响 |
|---|---|
| 0011：有确认人的清单必须有确认时间 | 旧系统中"已确认但没有时间"的清单，需要业务决定后再导入 |
| 0012：SERVICE 主体不能对应自然人 | 旧系统中的"服务账号人员"须改为无自然人的 SERVICE 主体 |
| 0016：个案与其资源须同一家庭、同一主体 | 导入顺序：先导入家庭与人员，再导入申请或案件，最后导入个案并引用 |
| D-10：`SELF_DECLARED_LEGACY` 监护不能经 API 新建 | 旧的自述监护关系需要另批的对账流程（补充 V1.2 D-10 第 3 条） |
