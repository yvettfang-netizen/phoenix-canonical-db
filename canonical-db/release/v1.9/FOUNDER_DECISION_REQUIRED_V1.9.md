## A. 需要立即决定（阻断 0018）

### D-1 数据库对象属主模型

| 项 | 内容 |
|---|---|
| 现状 | 27 张表、100 个函数（94 个 SECURITY DEFINER）全部属于超级用户 `phoenix_bootstrap` |
| 方案 | 转移给 NOLOGIN、NOSUPERUSER、NOBYPASSRLS 的 `phoenix_canonical_schema_owner` |
| PoC 结果 | PG16 与 PG17 完整 F10 通过，意外失败 0（`release/v1.9/DATABASE_OWNER_SECURITY_DECISION_V1.0.md` 第 3 节）|
| 代价 | 属主需要 `pg_read_all_stats`（否则上下文绑定失效）。**这使属主可读取其他会话的 SQL 文本，其中可能包含一次性票据的 UUID**（风险 R-1）|
| 选项 | (a) 批准转移，并接受 R-1；(b) 批准转移，但要求先找到不依赖 `pg_stat_activity` 的上下文绑定方式（需要架构变更，另立项）；(c) 维持现状，把超级用户属主列为长期风险 |
| **建议** | (a)，前提是 D-2 与 E-R6 修复先完成。理由：94 个 SECURITY DEFINER 函数以超级用户身份执行，风险大于 R-1；R-1 的利用需要先找到函数体内的注入点，而函数体没有动态 SQL |

### D-1b 恢复方式（与 D-1 联动）

| 项 | 内容 |
|---|---|
| 现状 | 三条恢复路径都使用 `pg_restore --no-owner`，恢复后所有对象属主变回超级用户 |
| 选项 | (a) 去掉 `--no-owner`，恢复前必须先创建属主角色（需要修改 restore.sh 与 restore_drill.sh，并重新演练）；(b) 保留 `--no-owner`，每次恢复后执行属主转移脚本并检查 |
| **建议** | (a)。理由：(b) 依赖人工记得执行，容易遗漏 |
