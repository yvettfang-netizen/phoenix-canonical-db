# Operations Entitlement Reference Contract Draft V1.0

**Status:** DRAFT / NOT EFFECTIVE  
**Gate:** D-8  
**Scope:** Canonical PostgreSQL greenfield database; synthetic and empty-data stages only  
**Owner:** Pending Founder designation

This draft converts the existing D-8 design notes into a reviewable contract. It does not reuse Operations OS data, IDs, credentials or assets. It does not authorize Migration 0021 until the decision record in `FOUNDER_DECISION_D8_V1.0.md` is signed.

## 1. Authority and system boundary

1. Operations remains the authority for orders, contracts, packages, payments and entitlement issuance.
2. Canonical stores only an entitlement reference, the subject and family it applies to, product scope, validity interval, lifecycle state and source event metadata.
3. Canonical never stores price, payment instrument, invoice, discount, commission or contract-document content in `operations_ref`.
4. An entitlement does not create Consent, guardianship, advisor assignment, channel authorization or permission to read sensitive learning data.
5. Missing, ambiguous, expired or revoked references fail closed.

## 2. Recommended reference identity

The recommended key is the pair `(source_system, external_entitlement_id)`.

| Field | Recommended rule | Decision status |
|---|---|---|
| `source_system` | Stable lowercase code, 2–40 characters, pattern `[a-z][a-z0-9_-]*` | Pending approval |
| `external_entitlement_id` | Opaque stable source identifier, 1–200 characters; Canonical does not parse business meaning from it | Pending approval |
| Canonical ID | UUIDv7 generated by Canonical | Covered by the effective Canonical identity baseline |
| Idempotency | Unique `(source_system, external_entitlement_id)` | Pending approval |

No `ord_`, `ent_` or other business prefix is assumed. If Operations requires a prefix or checksum, it must be supplied as a source contract before implementation.

## 3. Product separation

| `product_kind` | Required scope | Forbidden implication |
|---|---|---|
| `EDUCATION_SERVICE` | Subject and family | Does not grant course or ASKWISE access |
| `COURSE` | Subject, family and a concrete course identifier | Does not grant ASKWISE or learning-sensitive-data access |
| `ASKWISE` | Subject and family | Does not grant course or Education service access |

The three product kinds are evaluated independently. A single external reference must represent exactly one product kind.

## 4. Validity and lifecycle

Recommended lifecycle values are `ACTIVE`, `REVOKED` and `EXPIRED`.

An entitlement is valid only when all conditions are true at query time:

- status is `ACTIVE`;
- `valid_from <= transaction_timestamp()`;
- `valid_until IS NULL OR transaction_timestamp() < valid_until`;
- `revoked_at IS NULL`;
- subject, family, product kind and optional course scope match the request;
- the source reference is not superseded.

Recommended rules:

1. `valid_until` is an exclusive upper bound.
2. There is no grace period in Canonical.
3. Revocation takes effect on the next database authorization check after the revocation event is accepted.
4. A revoked or naturally expired row cannot become active again. A new source grant creates a new reference or a new source-qualified version.
5. Historical rows are append-only except for the controlled transition from `ACTIVE` to `REVOKED` and the recording of source event metadata.

These rules require Founder approval because they determine product access semantics.

## 5. Source interface

Recommended interface: an authenticated Operations service calls a SECURITY DEFINER database API through an INTERNAL context. Direct table writes are denied.

Minimum message fields:

| Field | Purpose |
|---|---|
| `source_system` | Source authority identifier |
| `source_event_id` | Idempotent event identifier |
| `external_entitlement_id` | Stable source reference |
| `event_kind` | `GRANT`, `REVOKE` or `REPLACE` |
| `occurred_at` | Time the source event occurred |
| `subject_person_id` | Canonical Person target |
| `family_id` | Canonical family target |
| `product_kind` | One of the three independent product kinds |
| `course_id` | Required only for `COURSE` |
| `valid_from`, `valid_until` | Source-approved validity interval |

Recommended delivery behavior:

1. At-least-once delivery is accepted through `source_event_id` idempotency.
2. Duplicate events return the previously recorded result and do not create a second active entitlement.
3. Out-of-order events are rejected unless the source version proves that the event is newer.
4. Revocation notification target is no more than 60 seconds from the source decision to Canonical acceptance. This value is a proposal and is not effective until signed.
5. Rejected events are audited without storing secrets or payload bytes.

## 6. Database access boundary

| Actor | Proposed capability |
|---|---|
| Operations SERVICE | Register and revoke through controlled functions; no direct table DML; no general business-table read |
| Application SERVICE | Call a boolean entitlement check for the current subject and requested product scope |
| Student / family | No raw Operations identifier read in the first implementation |
| Guardian | No raw Operations identifier read in the first implementation |
| Advisor / partner | No entitlement-reference read |
| Migrator | Create schema objects only |
| Reader / health | Schema and ledger health only; no entitlement rows |

The first implementation exposes only a boolean authorization result and reason code. This avoids making external order or entitlement numbers part of the family-facing contract before Operations approves their visibility.

## 7. Integrity controls required in Migration 0021

1. Subject must exist in `core.people` and have a matching `core.student_profiles` row when the product requires a student.
2. Subject must belong to the supplied family.
3. `course_id` is required for `COURSE` and forbidden for other product kinds.
4. Validity interval must be well formed.
5. Source event and source reference uniqueness must be enforced.
6. RLS is enabled and forced. Runtime roles receive no direct table DML.
7. SECURITY DEFINER functions use a fixed `search_path`; PUBLIC execution is revoked.
8. Every allow and deny decision records an audit reason code through the existing controlled audit path.
9. No entitlement operation can create or modify Consent.
